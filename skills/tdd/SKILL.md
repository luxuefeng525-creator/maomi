# TDD（红 → 绿）

这个技能是让循环产出**值得留下的测试**的参考：好测试长什么样、测试该放在哪、有哪些反模式、循环的规矩。每一节在循环开始前和进行中都要用，不是事后补。

探索代码库时，若有 `GLOSSARY.md` 先读，让测试名和接口用词跟项目领域语言一致；碰到的区域有 ADR 就遵守。

## 好测试的标准

测试通过**公开接口**验证**行为**，不验实现细节。代码可以整个重写，测试不变。好测试读起来像一条规格：`用户可以用有效购物车结账` 直接告诉你系统有什么能力，且因为不关心内部结构，重构后它照样活。

判据一句话：**重构之后它会不会假报警？会，就是坏测试。**

## seam：测试放在哪

seam 是你测的公开边界——一个能从外面观察行为、不必伸手进去的接口。**测试只住在 seam 上，永远不扎进内部。**

**只在事先说定的 seam 上写测试。** 动手前先写下这次要测哪些 seam 并跟用户确认；没确认的 seam 一条测试都不写。测不全，所以先把 seam 定下来，测试力气才会落在关键路径和复杂逻辑上，而不是散在每个边角。

要问的：「公开接口是什么？这次测哪几个 seam？」每个候选 seam 给一句话说明它**抓得住什么、抓不住什么**。

## 反模式（见到就停）

- **耦合实现**：mock 内部协作对象、测私有方法、或走侧门验证（去查数据库而不是走接口）。特征：行为没变，一重构测试就红。
- **同义反复**：断言用跟实现同样的算法重算期望值（`expect(add(a,b)).toBe(a+b)`、手工按同样路径推出来的快照、常量断言自己等于自己），于是它靠构造通过，永远不可能不同意代码。期望值必须来自**独立的事实源**：已知正确的字面量、算过的样例、规格。
- **横向切片**：先把测试全写完，再写全部实现。批量测试验的是**想象中的**行为——你测的是东西的**形状**而不是用户可见行为，测试因此对真实改动静默，而你在还没理解实现时就锁死了测试结构。改走**垂直切片**：一条测试 → 一份实现 → 重复，每条测试是上一轮教了你什么之后的**曳光弹**。

## 循环的规矩

- **红在绿前。** 先写会失败的测试，再只写足够让它通过的代码。不预判后续测试，不加投机功能。
- **一次一片。** 一个 seam、一条测试、一份最小实现，一个循环。
- **重构不在循环里。** 它属于评审阶段（见 `code-review` / `agent-review`），不属于红→绿这一段。
- **测试红了为了对的原因。** 断言失败，不是编译错误、不是导入错。红了先看失败信息是否正是你预期的理由。
- **绿了不许偷偷加料。** 让测试通过就停；想到的额外改动记下来，下一轮再说。

## 切片怎么切

按**用户可观察的能力**切，不按层切（不是"先写所有 model 再写所有 controller"）。一片的粒度：能在一次循环里写出一条会失败的测试并让它转绿。

难以切片时，说明接口还没想清——这时该去用 `code-review` 里的模块/接口词汇，或先用 `grilling` 把接口问清楚，而不是硬切。

## 什么时候不该用

- 已有行为要**证明没坏** → `verify-and-stop`。
- 只是窄修一处、且回归证明足够 → `surgical-patch`。
- 行为不变的结构调整 → `safe-refactor`（它自带走红→绿保底）。
