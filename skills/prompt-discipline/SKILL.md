# 提示词与推理纪律

触发词：AI 偷懒 / 推理不深 / 答得浅 / 先思考再动手 / 提示词优化 / 沉淀技能 / 复盘 / 自进化

## 适用

- 用户抱怨回答浅、偷懒、没推理、直接给结论。
- 需求模糊，需要先变成可执行、可验收的指令。
- 同类提示词或流程反复出现，要沉淀成模板、命令或技能。
- 复盘失败任务，要把坑变成规则。

## 不适用

- 纯事实查询、单行改动：直接做，不套流程。
- 已有明确验收标准的执行任务：交给 `project-orchestrator` 定档推进。

## 一、把需求变成可执行指令

每条需求至少写清四段，缺一段先问，不猜：

| 段 | 写什么 | 反例 |
| --- | --- | --- |
| 目标 | 要改变的用户可见结果 | 「优化一下」 |
| 边界 | 可改目录、不能动的接口与文件 | 未写范围 |
| 验收 | 可逐项勾选、含验证命令 | 「能跑就行」 |
| 反例 | 明确不要什么 | 只写要什么 |

模板见 `references/templates.md`。

## 二、反偷懒协议（每次任务必须走）

1. **复述**：开工前用 3 行写清目标、边界、验收；与用户理解不一致就先停。
2. **假设**：修 Bug 或做架构选择时，先列至少 2 个可证伪假设，再决定验证顺序。
3. **意图**：每次工具调用前用一句话说明「这次调用要验证什么」；调用后核对结果是否支持该假设。
4. **失败**：写「观察到 → 假设 → 下一验证」，禁止原样重复同一动作；连续 2 轮没进展就换思路并说明已试过什么。
5. **收尾**：给命令输出、文件路径、数字；把未验证项与推测单列，不用「应该」「大概」代替验证。

## 三、推理深度按任务分档

| 档 | 触发 | 要求 |
| --- | --- | --- |
| 快答 | 事实查询、查路径 | 直接答，带来源 |
| 标准 | 单文件改动、单点修复 | 3 行推理摘要 + 证据 |
| 深推 | 跨端、改库表、疑难 Bug、方案选型 | 问题分解 + ≥3 个假设 + 验证顺序 + 反例 |

执行器侧已把推理强度写进 `tests/behavior/providers.json`：codex 用 `-c model_reasoning_effort=high`，mimo 用 `--variant high`。档位低时不要靠加长提示词硬凑。

## 四、把重复沉淀成资产

| 重复次数 | 动作 | 落点 |
| --- | --- | --- |
| 同一提示词第 3 次 | 抽成一句话模板或命令 | 项目 rules、命令库 |
| 同一流程第 3 次 | 沉淀成 Skill：写适用/禁用 + 最小示例 | `skills/<name>/SKILL.md` |
| 同一坑第 2 次 | 记 pitfall → 聚类提案 → 人工确认 | `.agent-memory/` → `scripts/evolve.mjs` → `rules/agent-rules.md` |

进化闭环：`memory.mjs append` 记坑 → `evolve.mjs` 聚类出提案 → 人确认后写规则或技能 → 下次执行自动注入。没有人工确认，不自动改规则。

## 五、交付前检查表

- 目标、边界、验收是否都写了？
- 结论是否有命令输出或文件证据？
- 未验证项、推测是否单列？
- 引用是否给了来源路径或链接？
- 这次踩的坑是否已记入记忆？
