# 子代理并行拆解（L2 大任务的提速通道，按需加载）

本文件只在 **L2 且任务可被拆成独立模块** 时加载。对标 `obra/superpowers` 的
subagent-driven-development，但修正其一条过严的规则：superpowers 禁止并行派发实现
子代理（怕冲突）。冲突的根因是 **文件所有权重叠**，不是并行本身。本协议的立场是：

> **隔离文件所有权 + 共享契约先建 + 叶节点并行**，既提速又不冲突。这是被允许的并行方式。

禁止的是：同一个上下文里让一个 agent 同时改多个模块（上下文污染 + 误改），
以及让两个子代理写同一批文件（互相覆盖）。

## 何时启用（满足全部）
- 已定档 **L2**，且任务含 **≥3 个相对独立的模块 / 页面 / 数据域**；
- 能画出**无重叠的文件所有权契约**（每个子任务独占一组文件 / 目录）；
- 有清晰的接口契约或共享类型（可先串行敲定）。

不满足（任务紧耦合、单模块、无法隔离所有权）→ 走普通单线 8 环，不并行。

## 何时不要用子代理（对标 Claude Code 官方）
- **小任务 / 快修**：委派开销大于收益，主会话直接做。
- **同一个文件要改**：两个子代理并行写同文件 = 冲突，放同一上下文。
- **强依赖串行**（第二步要第一步的完整输出）：单会话更干净，别搞子代理接力。
- **子代理之间要互相协调**：它们彼此不能对话；需要协调就同一会话，或用 agent teams（更重更贵）。

## 结构化上下文传递（只给最小上下文）
派发时控制器只传一个结构化对象，**不要把父会话历史整段塞过去**（这是多代理行为矛盾的常见根源）：
```json
{
  "task": "一句话目标",
  "scope": ["src/auth/login.ts", "src/auth/session.ts"],
  "constraints": ["不改公开 API", "保留现有测试"],
  "acceptance": ["登录失败返回 401", "新增单测通过"],
  "output_schema": { "files_modified": ["string"], "summary": "string" }
}
```
子代理只拿这个对象 + 需要的文件全文，回报按 `output_schema` 给「改了哪些文件 + 摘要」，主上下文只收这份摘要。

## 五步流程
1. **调研一次（控制器自己做，或派一个只读 research 子代理）**
   摸清涉及哪些模块、公共契约（类型/接口/路由/设计令牌）在哪。只做一次，结论写进计划，
   不要每个子代理各查一遍（浪费且结论不一致）。
2. **拆解成原子任务 + 划所有权**
   每个任务：明确目标、文件所有权（独占目录/文件清单）、接口契约、可测验收标准。
   用 `node scripts/decompose.mjs` 拿结构依据：它扫描源码根、分析跨模块 import，
   把模块分成 `LEAF`（无向外依赖，可并行）/ `HUB`（被多人依赖，先串行建）/ `PEER`（相互依赖，串行）。
3. **先建共享契约（串行，不可并行）**
   HUB 模块（公共类型、接口、路由表、设计系统变量、数据模型）必须先完成并通过编译/类型检查，
   再放叶节点并行。契约未定就并行 = 各写各的，必冲突返工。
4. **派发实现子代理（叶节点可并行）**
   - 每个子代理 = **全新上下文**，只给「它需要的全部内容」：任务目标、文件所有权清单、
     契约摘要、验收标准、相关代码全文（**不要让它去读计划文件**，直接给文本）。
   - 并行派发**仅限所有权不重叠的 LEAF**；HUB/PEER 仍串行。
   - 模型分层：机械 1–2 文件任务用便宜模型；多文件集成用标准模型；架构/审查用最强模型。
   - 子代理回报四态之一：`DONE` / `DONE_WITH_CONCERNS` / `NEEDS_CONTEXT` / `BLOCKED`。
5. **两阶段审查 + 集成（每个任务后，或并行批后统一）**
   - 阶段一 **规格合规**：实现是否真满足验收标准（不过 = 打回重做）；
   - 阶段二 **代码质量**：安全、可维护、无残留调试代码、口径一致。
   - 审查可由子代理执行（给 diff + 规格），但**不能让实现者自我审查替代**；任一阶段有问题
     就 `DONE_WITH_CONCERNS` → 原实现者修 → 再审查，直到通过。
   - 全部返回后：控制器在**独立分支 / worktree** 集成（`node scripts/git-atomic.mjs worktree <名>`，见 `references/git-workflow.md` §2），跑全量测试 + `node scripts/verify-visual.mjs` 截图自检，提交用 `git-atomic.mjs plan` 原子拆分，再走 `references/workflow.md` 的环 6–8。

## 连续执行纪律
派发后不打断问「要继续吗」。只在三种情况下停：**BLOCKED 无法解 / 出现真正阻断进度的歧义 /
全部完成**。状态与进度记到 `.ai-workflow/sdd/progress.md`（纯文本账本），使长任务在上下文
压缩后续命，不丢进度。

## 安全红线（出现即纠）
- 两个子代理 **写同一批文件**（重叠所有权）→ 必丢改动，绝不允许；
- 跳过任一阶段审查（规格 OR 质量）；
- 共享契约未定就放并行叶节点；
- 未获同意在主分支直接实现（用分支 / worktree 隔离）；
- 让子代理「去读计划文件」而非直接给全文（它读不到你的上下文）；
- 接受「差不多」的规格合规（审查出问题 = 没完成）；
- 实现者自我审查替代独立审查。

## 与禁令的 reconciling
`SKILL.md` 第三条的「禁多模块并发改」指 **单 agent 在同一上下文 juggling 多模块**（污染 + 误改）。
本协议是**被允许的、安全的并行形式**：每个子代理独占文件、契约先行、审查兜底。二者不冲突——
前者是「乱改」，后者是「有序并行」。
