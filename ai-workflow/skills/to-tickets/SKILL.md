# 转工单

把计划、规格或当前讨论拆成**工单**：每张都是**曳光弹**式的垂直切片，并声明**拦着它**的工单。

## 流程

### 1. 收上下文
就用对话里已有的东西。用户给了引用（规格路径、issue 号或链接）就取来读完整正文和评论。

### 2. 探仓库（可选）
还没探过就先探，理解现状。工单标题和描述用项目领域词汇，遵守相关区域的 ADR。顺手找**预重构**机会：**先把改动变简单，再做那个简单的改动。**

### 3. 切垂直切片
- 每条切一条**窄但完整**的路径，穿过所有层（数据、接口、UI、测试）——**垂直，不是某一层的横切**。
- 做完一条能**单独演示或验证**。
- 每条**塞得进一个干净的上下文窗口**。
- 预重构排在最前。

给每张工单标**前置边**：哪些工单必须先完成。没有前置边的可以立刻开工。

### 4. 大范围重构是例外
**大范围重构**是那种**一处机械改动（改列名、改共享符号类型）就掀翻整个代码库**的活，几千个调用点同时断，没有任何垂直切片能绿着落地。别硬塞进曳光弹，按**扩张—收缩**排：

1. **扩张**：新形式与旧形式并存，什么都不坏。
2. **迁移**：按影响半径分批（按包、按目录）搬到新形式，每批一张工单，由扩张那张拦着。旧形式还在，所以每批都能保持绿。
3. **收缩**：没有调用方了，删掉旧形式，这张由所有迁移批次拦着。

连批次都保持不了绿时，就再拆细，直到每批能独立验证。

### 5. 发布
- 有工单系统（GitHub Issues 等）就按上面结构建，用原生 blocking 关系。
- 没有就落到 `tickets/`，一张一个 markdown 文件，前置边写成正文里的一行 `被拦于: T-001, T-002`。**别硬造一套系统。**

## 每张工单写什么

1. **一句话目标** —— 做完之后什么能力可用。
2. **验收** —— 怎么证明它成了（可执行的检查，不是"看起来对"）。
3. **前置边** —— 拦着它的工单。
4. **要动的 seam / 模块** —— 一句话，不写代码。
5. **测试** —— 从哪测、测什么。

## 别做

- 不要横切（"先写所有 model"），那是批量测试的温床。
- 不要拆得一张工单塞不满一个窗口却要开十个。
- 不要把没验证的假设写成验收条件。
