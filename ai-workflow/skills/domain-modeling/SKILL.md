# 领域建模

接口设计的好坏在**维护者脑子里要装多少东西**。本技能给一套共用词汇，让"这个接口是不是太浅了"能被具体地说出来。

## 核心词汇

- **模块**：任何有接口和实现的东西——函数、类、包、跨层切片都算。不特指某个文件。
- **接口**：调用方为了用它**必须知道**的一切：类型、约束、错误模式、顺序要求、配置。不只是签名。
- **深度**：接口的复杂度与实现的复杂度之比。**深模块**=简单接口套着大实现。**浅模块**=接口跟实现一样复杂，调用方什么也没省下。
- **信息隐藏**：实现里**可能变**的决定不泄漏进接口。泛化过度（过早抽参数）跟泄漏一样有害。
- **错误**：**叫得响的错误是好事**。能把错吞掉的接口藏起了行为，比抛异常更危险。

## 怎么用

设计或评审接口时按这五问过一遍：

1. 调用方要读多少东西才敢用？**太多 → 接口太浅。**
2. 实现里哪些决定会变？**变了会不会破调用方？会 → 泄漏了。**
3. 参数是不是为了"以后可能不一样"而抽的？**是 → 泛化过度。**
4. 出错时调用方能否知道？**吞掉了 → 坏接口。**
5. 换个实现，调用方要改吗？**要改 → 接口绑死了实现。**

## 用力方向

- 往**深处**走：把复杂度推进入实现内部，让接口变小而稳。
- 宁要**两个窄而明确的函数**，不要一个带五个 flag 的"万能"函数。
- 名字用**领域语言**（用户和业务怎么说），不用结构语言（`DataProcessor`）。名字统一了才写进 `GLOSSARY.md`。

## 和别的技能的分工

- 要**问清需求**再设计 → 先 `grilling`。
- 要**落地成文档** → `to-spec`。
- 结构已经乱、要**行为不变地重整** → `safe-refactor`。
- 要**验一遍**这些决定 → `code-review` / `agent-review`。
